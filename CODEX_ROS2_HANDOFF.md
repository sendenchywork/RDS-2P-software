## Важное ограничение архитектуры

Существующая физика MuJoCo выполняется в браузере пользователя. Веб-сервер выдаёт файлы, модели и библиотеки. Открытие страницы по IP не создаёт автоматически одну общую серверную симуляцию: разные вкладки имеют отдельные экземпляры мира.

Базовый план сохраняет физику в браузере, как указано в `TASK.md`. Сервер обеспечивает доставку сообщений. Если пользователь или руководитель явно потребует единую физику на сервере, сначала пересмотри архитектуру: это отдельное изменение объёма работ.

Начальный прототип рассчитан на один ROS-клиент и одну вкладку симуляции. Не обещай независимость нескольких сессий без маршрутизации по идентификатору симуляции.

## Существующие интерфейсы

Моторный узел подписывается на `motors/commands` с типом `ftservo_ros/msg/MotorCommands`. Это относительное имя; без namespace оно разрешается в `/motors/commands`.

`MotorCommands.msg`:

```text
std_msgs/Header header
MotorCommand[] commands
```

`MotorCommand.msg`:

```text
uint8 motor_id
float64 target_position
float64 target_velocity
float64 target_acceleration
bool ignore_limits
```

Положение задано в радианах двигателя, скорость в рад/с, ускорение в рад/с². Проверь фактическую обработку полей, включая нулевые значения, в реализации моторного узла. Комментарий «опциональные» в `.msg` сам по себе не создаёт nullable-поля или признак отсутствия значения.

Моторный узел также публикует `motors/states`, `motors/telemetries`, `motors/joint_mapping` и принимает `motors/params`.

Не отождествляй `motor_id` с индексом актуатора. Верифицируй отображение ID → имя мотора → сустав → актуатор по конфигурациям и модели.

Порядок актуаторов в изученном браузерном коде: `[fl, fr, bl, br] × [leg_block, hip, shin]`. Для каждого актуатора проверяй адрес в `qpos` и `qvel`: положение свободного корпуса означает, что первые 12 элементов этих массивов не равны автоматически 12 углам ног.

`data.ctrl` — управляющие значения; `data.qpos` и `data.qvel` — фактическое состояние. Смысл `ctrl` определяется моделью актуаторов. Для текущего пути управления используются целевые углы, но сверяй это с MJCF.

`setLivePose` принимает доли диапазона 0..1, а не радианы мотора. Нельзя передать туда `target_position` без преобразования. Для голени угол сустава зависит от двух моторных углов. Частичная команда одному мотору должна корректно учитывать сохранённые цели остальных моторов.

Не используй `setLiveAngles` как безусловно безопасный ограничитель: изученная реализация может разрешать выход за пределы через `noLimit`. Политику ограничений внешних команд определи явно.

## Предложенная схема обмена

Ниже — предварительное решение, которое нужно проверить минимальным сквозным прототипом. Требование пользователя — Zenoh; конкретный вариант его интеграции руководителем не зафиксирован.

```text
Терминал или программа ROS2
  → топик /motors/commands
  → наш ROS2-адаптер рядом с ROS-пользователем
  → Zenoh по сети
  → сервер Zenoh с remote-api
  → JavaScript-клиент в браузере
  → проверка команды и преобразование моторных углов
  → управление MuJoCo перед шагом физики
```

Предлагается отдельный Python ROS2-пакет, условное имя `rds_2p_web_bridge`, использующий `rclpy` и Python API Zenoh. Он принимает типизированные ROS-сообщения и передаёт выбранные поля в JSON через согласованные Zenoh keys. Обратный путь восстанавливает нужные ROS-сообщения.

Это прикладной мост для определённых интерфейсов, а не универсальная поддержка всех ROS-топиков в браузере. JSON между адаптерами не следует выдавать за штатную сериализацию ROS2.

Сервер Zenoh и remote-api — готовые компоненты. JavaScript/TypeScript API подключается к remote-api, поэтому браузеру недостаточно адреса обычного Zenoh TCP listener. Зафиксируй совместимые версии сервера, плагина и клиентов.

Не смешивай этот вариант с `rmw_zenoh` или `zenoh-bridge-ros2dds`. Это другие способы интеграции, с другими соглашениями маршрутизации и представления сообщений. Если выяснится, что нужен именно один из них, обоснуй изменение схемы до реализации.

Официальные источники для проверки актуальных API и совместимости:

- https://github.com/eclipse-zenoh/zenoh-ts
- https://github.com/eclipse-zenoh/zenoh-python
- https://github.com/eclipse-zenoh/zenoh
- https://github.com/eclipse-zenoh/zenoh-plugin-ros2dds
- https://github.com/ros2/rmw_zenoh

## План реализации и проверки

1. Проверить окружение и исходное состояние.

   Найти проект, прочитать локальные инструкции, проверить изменения и доступные ROS2/WSL/Linux/Docker-инструменты. Проект ориентируется на ROS2 Humble, но среду установки ещё нужно установить фактически. Выбрать минимальный способ запуска ROS и генерации сообщений. Учесть, что сборка всего `ftservo_ros` может тянуть библиотеку физических сервоприводов; сначала изучить зависимости, а не устанавливать весь роботный стек.

   Готовность: известны ОС, версия ROS2 и место запуска компонентов; доступны требуемые типы сообщений. Установка и запуск воспроизводимы.

2. Зафиксировать минимальный контракт обмена.

   Определить ROS-топик и тип, Zenoh key, формат JSON, единицы измерения и проверку входных данных. Решить, что означает частичная команда, как выбирается симуляция и какие поля поддерживает первая версия. Начать с положения; неподдерживаемые режимы явно обозначить или отклонять, а не молча изображать полную поддержку скорости и ускорения.

   Готовность: есть один пример команды и понятная таблица соответствий полей. На ROS-стороне сохраняется существующий интерфейс моторных команд.

3. Доказать сквозную доставку без движения робота.

   Поднять Zenoh с браузерным подключением. Реализовать минимальный ROS2-адаптер и браузерный приёмник, пока выводящий данные в консоль. Сначала всё работает на одной машине. При необходимости временно проверить транспорт простым сообщением, но итог этого этапа должен использовать реальный `MotorCommands`.

   Готовность: публикация сообщения через `ros2 topic pub` приводит к появлению тех же ID и чисел в консоли браузера. Известно, какой процесс слушает какой адрес и порт. Команды запуска записаны.

4. Подключить один мотор к физике.

   Добавить явный режим внешнего управления. Исключить перезапись команд локальным проигрывателем, политикой походки и преследованием. Проверить mapping, радианы и знаки. Применять проверенную цель в согласованной точке цикла физики. Не выдавать кинематическую запись в `qpos` за управление мотором.

   Готовность: команда известному мотору предсказуемо меняет нужную часть ноги. Учтено связанное движение голени. Ошибочный ID и нечисловые значения отклоняются без порчи состояния.

5. Расширить управление на все 12 моторов.

   Реализовать полные и частичные команды, хранение актуальных целей, ограничения и понятное поведение при паузе, сбросе, отключении и возврате к локальному режиму. Выбрать правило для устаревших команд и потери связи. Различать одноразовую цель положения и непрерывный поток скоростных команд: для них могут требоваться разные правила таймаута.

   Готовность: поза задаётся из ROS2; изменение одного мотора не обнуляет остальные цели. Потеря связи и переподключение обрабатываются предсказуемо. Пределы поддержки полей задокументированы.

6. Проверить работу по IP.

   Разнести ROS2-отправителя с адаптером и сервер по разным компьютерам. Проверить адреса, порты, HTTP/HTTPS и WS/WSS, если используется TLS. Не оставлять `127.0.0.1` как адрес удалённого сервера. Для первой демонстрации использовать одну вкладку; явно обозначить ограничение многопользовательского режима.

   Готовность: команда с другого компьютера доходит до выбранной браузерной симуляции. Есть короткая инструкция повторения сценария.

7. Добавить обратную связь как следующий объём работ.

   Начать с `/joint_states` типа `sensor_msgs/msg/JointState`: имена суставов и фактические положения, скорости при корректном доступе к ним. Это суставные данные, а не готовые `MotorStates`; для последних потребуется обратное преобразование. Не публиковать целевые углы как измеренные. Определить частоту и семантику времени, включая паузу. Использование `/clock` и `use_sim_time` вводить согласованно, если оно требуется.

   Готовность: `ros2 topic echo /joint_states` показывает состояние симуляции, соответствующее наблюдаемому движению.

8. Зрение и дополнительные датчики после основного результата.

   При подтверждённой необходимости передавать изображение виртуальной камеры через выбранный ROS-интерфейс. Определить разрешение, частоту, кодирование, время и систему координат. Добавлять IMU или детекции отдельными этапами. Не придумывать температуру, напряжение или другие величины, которые модель физики не рассчитывает, без явно согласованной модели этих данных.

   Готовность: ROS-получатель видит действительно полученные из виртуальной сцены данные, а ограничения и источник каждого поля описаны.

## Проверки и итоговые материалы

Проверять код соразмерно изменениям. Особенно важны проверки сериализации, ID, единиц, знаков, частичных команд и конфликтов источников управления, а также сквозной запуск. Не считать успешный unit-тест доказательством работы сети или браузерной физики.

По завершении обязательной части нужны исходники адаптеров, конфигурация Zenoh, зафиксированные версии, инструкция запуска по терминалам и демонстрационный сценарий. Отдельно указать поддержанные поля, поведение при разрыве связи и ограничения одной сессии. Обновлять документацию по фактически проверенному поведению.

## С чего начать следующий чат

Кратко подтверди цель: первое сообщение `MotorCommands` из ROS2 должно пройти через Zenoh и появиться в консоли браузера. Затем проверь окружение и зависимости, предложи конкретный первый шаг и начни его в согласованном формате наставничества.

Не начинай с реализации камеры, изменения механики ног, переписывания симулятора или очередного большого обзора всего репозитория.
